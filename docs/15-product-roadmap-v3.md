## 0. 摘要（TL;DR）

V3 的目标不是"再做一遍 Hermes"，而是把 Spirit 已经走出的两条差异化路径——**桌面伴侣 + 接地式自进化**——从"机制层"推向"成效层"，并补齐让这两条路径真正稳跑的"中间件"。一句话：

> **V2 是"能跑"（v0.0.2 → v0.2.2，核心闭环 100%）；V3 是"能信"（让用户敢于把真实任务常驻交给 Spirit）。**

具体来说，V3 解决三件事：

1. **从"机制存在"到"机制稳定"**：自进化 RSI（`evolution/` 14 文件）和 Autonomy（`autonomy/` 4 文件）目前是"机制建好、单元测试绿"，但常驻循环只跑 DRS 单目标、BRS 广度并行和 Phase 3 冻结复用没接进 `autonomy/`。V3 要让它们真在常驻循环里跑起来，并产出可量化的"成效数字"。
2. **从"借来的简化版"到"自己的工程化"**：Spirit 核心 Agent 模块（conversation_loop / context_compressor / tool_executor / prompt_builder）当前是 Hermes 的"压缩 + 借鉴"（Spirit 模块头注释明说"参考 Hermes xxx"），V3 要补齐"错误恢复链 + 工具结果分类 + 截断多策略"等关键中间件，让 Agent 在工具失败 / 输出溢出 / 思考超时 / provider 切换时仍能继续推进，而不是卡死重试到耗尽迭代预算。
3. **从"个人开发者的桌面玩具"到"团队 / 长任务的可信伙伴"**：当前 Spirit 桌宠主要是单用户、单机、单会话的体验。V3 探索"长任务监控面板 + 团队共享会话 + 任务进度可视化"，让 Spirit 真正"活着"在用户的桌面上。

## 一、V2 复盘：已经做对了什么

### 1.1 核心闭环已 100% 跑通

- **Agent 核心**：`spirit/agent/` 19 个文件 / ~7,000 行

- **测试**：2,440 + 418 = **2,858 项测试通过**

### 1.2 已经走出的两条差异化路径

Spirit 不是 Hermes 的"二次开发"，它走的两条路是 Hermes 没有的：

| 路径 | Spirit 的实现 | Hermes 没有 |

|------|------|--------|

## 二、V3 产品愿景

### 2.1 一句话定位

> **Spirit V3 = 一个"敢常驻"的桌面 AI 队友：能接真实任务、能自我迭代、能在桌面上和你互动。**

### 2.2 V3 的三大产品形态（继承自 V2 + 强化）

```
                Spirit Agent V3
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
   桌面精灵(桌宠)   VSCode 扩展    Web Dashboard
       │               │               │
       └───────────────┼───────────────┘
                       ↓
              Spirit 后端 (本地服务)
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
    Agent 核心      自进化闭环      Autonomy 常驻循环
       │               │               │
       └─────── V3 三大支柱 ────────────┘
```

**V3 相对 V2 的变化**：
- 桌宠从"装饰 + 简单对话"升级为"任务监控面板 + HITL 入口 + 进度可视化"
- 后端从"运行 Agent 一次性任务"扩展为"运行常驻自主探索 + 多 session 监控"
- 自进化从"机制存在"升级为"机制稳定 + 成效可量化"

### 2.3 V3 核心场景（按重要性排序）

#### 场景 A：长任务的"安全管家"（**最高优先级**）

```
用户在桌宠输入："帮我重构 spirit 项目的 moa_loop 模块"
   ↓
Spirit 在 VSCode 中开始执行（多轮工具调用，可能持续 30+ 分钟）
   ↓
桌宠显示进度条："moa_loop 重构进行中... 第 12/40 步"
   ↓
遇到工具失败：桌宠弹气泡提示 + 用户点"自动恢复"或"换方案"
   ↓
完成后桌宠推送结果摘要 + 询问是否要把这次经验存进长期记忆
```

**V3 要解决**：进度可视化、HITL 决策、结果汇报。

#### 场景 B：常驻自主探索的"成就展示台"（**次高优先级**）

```
用户设定一个探索方向："帮我研究 LLM agent 的错误恢复机制"
   ↓
Spirit 在后台常驻（AutonomyLoop 跑 BRS 广度并行 + DRS 深度串行）
   ↓
桌宠每日推送日报："今天自主探索 3 个子问题，沉淀 2 条新经验"
   ↓
用户点击桌宠 → 看到可视化进度（自进化 wave / phase 状态）
   ↓
用户可以"暂停 / 改方向 / 验收 / 丢弃"
```

**V3 要解决**：BRS 真接进常驻、wave barrier 真实跑、Phase 3 冻结复用、成效可视化。

#### 场景 C：VSCode 深度集成的"信任升级"（**中等优先级**）

```
用户在 VSCode 中写代码
   ↓
Spirit 主动检测："这段代码有 3 个潜在问题，要不要我看看？"
   ↓
用户："好"
   ↓
Spirit 在 VSCode 中给出诊断（用 LSP + 内联 diff）
   ↓
用户验收 → Spirit 把这次"诊断模式"记进跨会话记忆
```

**V3 要解决**：LSP 集成的稳定性、错误恢复的鲁棒性（不会因为一个工具失败就崩）。

#### 场景 D：多 session / 团队共享（**探索性**）

```
开发者 A 在 VSCode 中和 Spirit 协作
开发者 B 通过 Web Dashboard 看到 A 的进度（只读）
开发者 A 把"重构经验"导出给 B 的 Spirit
   ↓
B 的 Spirit 接续 A 的记忆继续工作
```

**V3 要做 PoC，V4 才做产品化。**

### 2.4 V3 目标用户

| 用户 | 现有痛点 | V3 如何解决 |
|------|---------|------------|
| **个人开发者（单兵）** | 工具失败卡死、长任务失忆、不知道 Agent 在干嘛 | 错误恢复 + 进度可视化 + 经验沉淀 |
| **AI 探索者（自进化用户）** | 自进化跑了一晚上不知道结果、效果不直观 | BRS/Phase 3 真接 + 成效数字 + 日报 |
| **小团队（2-5 人）** | 经验无法共享、Agent 状态不可见 | 多 session 监控 + 经验导入导出（PoC） |
| **非目标用户**：云端 SaaS 用户、重度 IDE 用户、企业级 SLA 用户 | — | V3 明确不做 |

### 2.5 V3 明确不做

- ❌ 不做云端 SaaS（纯本地部署，与 V2 一致）
- ❌ 不做企业级 SLA / 99.99% 可用性
- ❌ 不做 Agent 自改源码自我升级（与 Phase 7 沙箱约束一致；自进化只改"经验"不改"代码"）
- ❌ 不做第二个 VSCode（V3 桌宠的核心价值是"陪伴 + 监控"，不是"替代编辑器"）

## 三、V3 战略支柱

V3 拆为三大战略支柱，每个支柱有明确的"成功度量"。

### 支柱 1：错误恢复与稳定性（**Reliability**）

**目标**：让 Agent 在"工具失败 / 输出溢出 / 思考超时 / provider 切换"等异常路径上不卡死。

**成功度量**：
- 工具失败循环次数从当前 ~8 次/任务降到 ≤2 次/任务
- OS 类别 420s 超时事故率从 100% 降到 0%
- 单任务平均耗时波动范围从 ±50% 降到 ±20%

**关键能力**（详见 `16-feature-roadmap.md`）：
1. 错误恢复链（`turn_recovery.py` 对齐）
2. 工具结果分类（`tool_result_classification.py` 对齐）
3. 截断多策略（`turn_truncation.py` 对齐）
4. 活性检测（`turn_liveness.py` 对齐）
5. **上下文压缩鲁棒性 v2（`context_compressor_v2.py`）**：补齐 Hermes 5,577 行 vs Spirit 410 行 间的 stall detection / 拒绝检测 / 确定性摘要路由 / route_pin / 微压缩 / 脱敏集成 6 项差距（Spirit 13.6× 落后）
6. **动态 prompt 组成（`prompt_composer.py`）**：按模型 / 任务类型 / 上下文动态调整 prompt，提升跨 provider / 跨任务的质量一致性（Spirit 4.8× 落后）
7. **准确率归因 + 提升（M-P1.0）**：把“低于 Hermes 不差”拆为“工具失败 / 输出溢出 / 上下文丢失 / prompt 不匹配 / provider 切换” 5 个归因维度，针对性补能力，把准确率从 62% 提升到 ≥72%

### 支柱 2：自进化成效可量化（**Measurability**）

**目标**：让自进化 RSI 从"机制存在"升级为"成效可证"。

**成功度量**：
- BRS 广度并行真实常驻跑（不再只跑 DRS 单目标）
- 每日/每周成效数字可见（探索了多少子问题、沉淀了多少新经验、复用了多少次冻结记忆）
- RSIAgent 论文的"三大失败模式"（探索打偏 / 校验放过 / 记忆固化）在 Spirit 上的发生率可观测

**关键能力**：
1. BRS/Phase 3 接线进 `autonomy/`
2. 接地层补齐：领域验证器（金融回测 / 代码 lint / 单元测试通过率）
3. 成效度量 harness：自动跑可重复的小 benchmark，记录前后对比
4. 日报与可视化：桌宠看 wave 状态 / 自进化记忆 hash / 经验沉淀次数

### 支柱 3：桌面伴侣体验升级（**Companion**）

**目标**：让桌宠从"装饰 + 输入框"升级为"任务监控 + HITL 入口 + 经验沉淀确认"。

**成功度量**：
- 长任务进度可视化覆盖率 ≥80%
- HITL 决策平均响应时间 <60s
- 经验沉淀的"主动确认率" ≥30%（用户在 Spirit 提议存经验时主动接受的比率）

**关键能力**：
1. 长任务进度面板（推送到桌宠）
2. HITL 决策面板（气泡 + 系统面板）
3. 经验沉淀确认（自进化写记忆前询问用户）
4. 任务历史回看（点桌宠 → 看到今天所有任务）

## 六、关键决策记录

### 决策 V3-D1：V3 不追 Hermes 100% 对齐

**结论**：Spirit 已经有"桌面伴侣 + 常驻自主"两条差异化路径，再花精力把 Hermes 100+ 文件全搬一遍是**模仿而非创造**。

**理由**：
- Spirit 的核心 Agent 模块头注释明说"参考 Hermes"，已经是借来的简化版
- Hermes 的 turn_recovery / subagent_lifecycle / review_engine 等高级特性是为"批量 benchmark runner"设计的，不完全适合 Spirit 的"常驻桌面伴侣"
- 资源有限：与其追 100% 对齐，不如把差异化路径做深

**取舍**：放弃的"对标"包括 subagent_lifecycle / turn_facade_lease / verify_hooks（这些是 Hermes 批量跑 benchmark 的特性，Spirit 用不上）。

**修订**：原决策“放弃 moa_alternation”**降级为 P3 评估（M-P3.2）**——AgentBench kg-2 实测遇到 strict-alternation 400 表明“主流 provider 不需要”这个判断**缺数据**，V3-2 调整为：在 V3.0.0 阶段跑 0.5 周复现 + 0.5 周决策，如果 3 个 provider 都修复不了则升级为 P2 实装，仅 1 个非主流 provider 则保持放弃。

**采纳的"对标"**：turn_recovery / tool_result_classification / turn_truncation / turn_liveness（这些是"让 Agent 不卡死"的中间件，Spirit 同样需要）；**新增采纳**：context_compressor v2 / prompt_composer（让 Agent 不“变傻”）；accuracy_attribution（让准确率提升有依据）。

### 决策 V3-D2：自进化走"领域验证器"而非"密封官方评测器"

**结论**：V3 不试图复刻 RSIAgent 的"真 VM + 视觉 + 密封评测器"。

**理由**：
- 密封官方评测器是 RSIAgent 论文的核心资产，Spirit 没有 benchmark 主办方身份
- Spirit 走"领域验证器"路线：用户配置自己领域的成功标准（金融→夏普 > 阈值 / 代码→lint 0 警告 + 单测通过 / 文档→结构完整 / 数据→回测准确率 ≥X%）
- 领域验证器是注入式设计（已有 `spirit/evolution/domains/FinanceDomain` 范例），扩展性好
- 用户的真实使用场景是"我自己的领域"，而不是"OSWorld benchmark"

**风险**：领域验证器不是密封的，存在 Agent "学会欺骗验证器"的可能。**缓解措施**：V3 增加"交叉验证"（用不同 LLM 实例验证同一个产物）+ 记忆固化前的"二次回放"。

### 决策 V3-D3：桌宠是"任务监控"而非"任务执行"

**结论**：V3 桌宠不直接执行任务（避免变成第二个 IDE），而是"长任务的可视化 + HITL 入口"。

**理由**：
- 任务执行属于 VSCode / CLI 场景，桌宠介入只会让用户分心
- 桌宠的核心价值是"陪伴 + 进度感知"，与"高效执行"是不同维度
- 任务执行需要密集交互，桌宠的轻量交互模型（气泡 + 菜单）不适合

**采纳**：桌宠推送进度、等待 HITL 决策、确认经验沉淀、回看历史。

**不采纳**：桌宠内嵌完整编辑器、桌宠内嵌文件浏览器、桌宠内嵌终端。
